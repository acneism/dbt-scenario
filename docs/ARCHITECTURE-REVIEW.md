## Подтверждённые дефекты

### P2. Хеш может описывать версию модели до копирования

Конструктор `Project` считает `project_hash` на исходном дереве, затем обходит файлы и копирует проект. Модель может измениться между хешированием и копированием. Тогда dbt получит новые байты, а отчёт запишет хеш старых. [project.py:96](../src/dbt_scenario/project.py#L96), [runner.py:118](../src/dbt_scenario/runner.py#L118)

Проверено независимо от PostgreSQL. В минимальном проекте обёртка над `copytree` меняет SQL с `select 1` на `select 2` непосредственно перед копированием. Рабочая копия содержит `select 2`, а `Project.project_hash` совпадает с исходным хешем для `select 1`. Хеш копии измерен до перезаписи профиля dbt.

Исправление — читать настройки и вычислять хеш по одной подготовленной копии до внутренних изменений dbt-scenario. При изменении смысла поля зафиксировать новую версию формата. Регрессионный тест должен воспроизвести правку в момент копирования и сверить хеш с рабочей копией.

### P2. В Markdown теряются причины ошибок уровня сценария

`summary.md` выводит общий статус и причины отдельных шагов. При ошибке до первого шага или при сбое очистки код причины может быть только в корне `summary.json`. CLI тоже печатает статусы шагов и может показать подсказку при наличии диагностики. Код ошибки очистки отдельно не выводится. [report.py:38](../src/dbt_scenario/report.py#L38), [cli.py:206](../src/dbt_scenario/cli.py#L206), [runner.py:245](../src/dbt_scenario/runner.py#L245)

Проверено на выходе настоящего `write_report`. При `overall_status=ERROR` и отсутствии выполненных шагов JSON сохраняет оба кода. В Markdown остаются общий `ERROR` и шапка таблицы.

Исправление — вывести `reason_code` и `cleanup_reason_code` в Markdown и CLI, когда поля заполнены. При ошибке очистки после завершённых шагов пользователь должен видеть, что сама проверка прошла, а ресурсы требуют внимания. Для вывода достаточно существующих безопасных кодов.
